## 1. What you have to do before it works

Three things, in this order. None of them is optional.

### 1.1 Run the migrations (on the HPC, inside the VPN)

```bash
psql -h /nfs/home/users/vpandya/databases/postgres_hpl_kb/socket -d hpl_kb \
     -f backend/migrate_all.sql
```

Idempotent — a no-op against a database that is already up to date. It now creates eight tables that
had no `CREATE TABLE` anywhere in git, and adds the five `registration_*` columns the new step
records its state in. **Without it the new step still runs but nothing shows as registered**, and
the UI will offer it forever.

### 1.2 Copy `backend/` to the cluster and restart the server

This is the step easiest to skip. `backend/tile_server_v2_.py` runs **on the HPC login node**, not
on your laptop — it shells out to `sbatch`, opens `.svs` files from scratch, and reaches Postgres
over a local socket. Running the updated folder on your Mac does **not** pick up any backend change.

```bash
# on the HPC
cd backend && python tile_server_v2_.py     # FastAPI on :8000
```

`app/` and `frontend/` run on your laptop and do pick up their changes directly.

### 1.3 Capture five `\d` outputs and send them back

These are the last tables whose real shape is not recorded anywhere outside the server, so a fresh
checkout still cannot build a complete schema:

```
\d hpc_dictionary
\d hpc_malignant_details
\d hpc_non_malignant_details
\d hpc_survival_analysis
\d+ slide_metadata
```

Append them to `backend/kb_live_schema_2026-08-26.txt`. `backend/tests/test_schema_coverage.py`
names them in its `KNOWN_UNCOVERED` set and will keep failing to cover them until they exist.

## 2. How to run it

```bash
# on the HPC, inside the VPN
cd backend && python tile_server_v2_.py

# on your laptop, with a tunnel to the login node
ssh -N -L 8000:localhost:8000 -L 5432:localhost:5432 beatson-hpc
streamlit run app/app_v28.py
```

The second `-L 5432` is not optional: the chatbot and three viewer helpers query Postgres directly
rather than through the API.

The React UI is an alternative to Streamlit, not a replacement — `cd frontend && npm run dev`, port
5173, same backend. It has the same six steps now. Note `frontend/node_modules` in this folder was
installed for a different architecture and its native binaries do not load here; run `npm install`
on whichever machine you use it from.

## 3. What changed

### The pipeline is six steps, not five

```
1 Tiling             submit_mask_tile_slurm.py     tiles + _tile_metadata.csv ON DISK
2 Packaging          make_hpl_hdf5.py              one gzip .h5
3 Feature extraction submit_feature_extraction.py  projections .h5     (GPU)
4 Classification     submit_cluster_assignment.py  assignments .csv    (CPU, faiss)
5 Registration  NEW  register_dataset.py           wsi_registry, wsi_metadata, dataset_config,
                                                   tile_coordinates, tile_registry
6 KB load            load_hpc_assignments.py       tile_registry.hpc_id + the aggregates
```

**Step 5 is new and step 6 is now gated on it.** Step 6 only ever `UPDATE`s
`tile_registry.hpc_id` — the row has to already exist. For a cohort that has never been in the
Knowledge Bank there is nothing to update, so its match rate is 0% by construction and it refuses.
That refusal was the only signal, and it names a match rate, which reads like a slide-naming bug.

Step 5 is gated on step 2, not step 4 — it reads tile identity out of the packaged `.h5` and the raw
slides and needs no cluster labels, so it can be done while the GPU work is still queued.

### The gap that would have bitten first

Before this, the only code anywhere that wrote `wsi_registry` was the interactive single-slide
drag-and-drop upload. **No bulk dataset run had ever registered a slide.** A Radiogenomics run would
have completed every stage, filled `tile_registry` and the aggregates, agreed with itself on every
row count — and every slide in the cohort would have 404'd in the viewer, because the viewer
resolves slide paths from `wsi_registry` alone. Nothing in the pipeline was in a position to notice.

All five tables are now written in **one transaction**, so that half-registered state is not
reachable by forgetting a command.

### Guards it will refuse on, and what each means

| refusal | what to do |
|---|---|
| a slide id matches two files under the raw directory | pick which file is really this cohort's; it will not guess |
| a tile or slide already belongs to a different `dataset_id` | two cohorts are claiming one slide — investigate, do not overwrite |
| this `dataset_id` already has rows | tick "Replace this cohort's existing rows" and preview again |
| the database has no `wsi_registry` (etc.) | you have not run §1.1 |

Reported but not fatal: slides with no raw file (tiles register, slide will not open), slides with
no Stage 1 metadata (no coordinates), slides carrying two `sample_id`s in the `.h5`.

### Other fixes

- **`slide_hpc_membership` is refreshed by step 6.** It looked unreferenced to a grep, but
  `app/hpc_chat_handlers_v23.py:334` enumerates every table with an `hpc_id` column and shows
  matching rows to the user — so its 19,493 stale rows from an older cohort were being served in
  answers about clusters.
- **The schema is in git.** Eight tables and the `dataset_id` column had no DDL anywhere;
  `migrate_all.sql`'s claim that it builds a fresh schema was false. `schema.sql` is a stale
  2025-10-23 dump that disagrees with the live `tile_registry` on its primary key and on `hpc_id`'s
  type; it now carries a header saying so. **Do not build a database from `schema.sql`.**
- **`CLAUDE.md` said Stage 1 wrote `tile_coordinates`.** It does not — it writes a CSV to disk. That
  one wrong line is the best explanation for why this gap survived: everyone believed the
  coordinates table filled itself.
- **`.gitignore`** now names the ~600 MB of CSV exports, the database dump and the GDC clinical
  download. They are still in this folder and are still not in git — keep it that way.

## 4. On the first real run

Do the 10-slide Radiogenomics dataset before the 14,044-slide one.

1. **Preview registration** and check `slides_without_files` and `ambiguous_slides` are both **0**.
   If slides have no raw file, their tiles register and the slides will not open.
2. Tick **"Also read slide headers"** only if you want `wsi_metadata` — it opens every slide file,
   which is minutes on a large cohort and nothing reads that table yet.
3. Commit registration, then **preview the KB load** and check the match rate is ≥95%. If it is
   still low after registering, that is a genuine slide-naming problem, not a missing step.
4. Restart the tile server once after registering if slides do not appear — `wsi_registry` is cached
   in memory at startup. The endpoint refreshes it, but a separate server process will not have.

None of this has been run against a real PostgreSQL. There is none on the machine it was written on,
so the DDL is transcribed and reviewed, not executed, and the endpoints are tested against SQLite.
**Preview before you commit.**
